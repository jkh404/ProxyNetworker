## 目标与顺序

按以下顺序推进，不以同时启动多个客户端项目替代逐阶段验收：

```text
阶段一：macOS 命令行客户端
    -> G1-CI：代码、原生构建和自动测试的开发门槛
阶段二：Avalonia 桌面可视化客户端
    -> G2：已验收平台的真实工作流与 Mac 预览版 CI 验证
阶段三：Avalonia Android 宿主与原生 VPN
    -> G3：分架构构建、实际数据面与移动生命周期验收

后续有 Mac 真机时：
    -> G1-REAL：补齐 Mac CLI/GUI 真机验收，再决定正式支持范围
```

按后续用户要求，桌面与 Android 共用 Avalonia/TKCode.Arc 界面和网络核心，Android 已同步开展实现与测试，不再受旧版“仅评估、不建立工程”安排约束。独立 CLI 保留。没有 Mac 真机时仍不宣称 Mac 已完成真实联网验收；Android 模拟器也不代替 ARM64 手机或应用商店验收。

## 现有基础与约束

- [Core](../ProxyNetworker.Core/) 已包含协议、AES-GCM、UDP 直连、Mesh Route、探测和 Relay Fallback，应优先复用，不为新增平台另写一套协议。
- [ITunDevice](../ProxyNetworker.Core/ITunDevice.cs) 是已有设备边界；[TunDeviceFactory](../ProxyNetworker.Core/TunDeviceFactory.cs) 已新增 macOS 后端，并通过双架构原生 CI，不改变 Windows/Linux 的平台选择。
- [Client](../ProxyNetworker.Client/) 已支持配置驱动、无参数启动和 Token 单实例锁。继续保留，不把 GUI 作为命令行或后台运行的前提。
- 当前本地配置以 `appsettings.json` 为来源，保留已有配置加载兼容性。GUI 不建立另一份独立且会发生冲突的 Token/网络配置。
- Avalonia 是界面框架，不提供本项目所需的虚拟网卡、管理员授权或 Android `VpnService` 实现。[^R4][^R5]
- 框架支持某个平台、项目能编译、自动测试通过、真实数据面通过和正式发布，是不同的完成状态。
- GitHub 提供 macOS 托管 runner，可作为当前原生构建和自动测试的候选环境；具体镜像、架构及权限在配置工作流时核对。CI 结果不能替代物理网络变化、睡眠唤醒或人工交互验收。[^R8]

## 贯穿各阶段的原则

1. **网络核心只维护一份。** 平台差异留在设备、权限、服务生命周期和打包层；避免 UI ViewModel 承担路由、加密或重连逻辑。
2. **默认安全，能力不足时明确降级。** 保持 AES-GCM 默认开启；可选 offload 不可用时使用既有普通路径，不用关闭认证或机密性换取兼容。
3. **不静默改协议。** 平台缺少 QUIC 能力时明确报告限制；不能假设服务端会接受偷偷改成 UDP 的连接。
4. **最小化特权。** 管理员权限只用于确有需要的接口、路由和后台工作进程操作，不把整个桌面 UI 长期作为 root/管理员运行。
5. **默认不接管全局网络。** 初期仅处理 Virtual Network 的虚拟网段；修改默认路由、全局 DNS、自动启动和始终在线均需独立设计与明确授权。
6. **能够停止，也能够恢复。** 只清理自身创建和确认归属的资源；连接失败、取消、异常退出及版本回退均不得破坏原有配置和正常上网。
7. **公开内容与现网数据分离。** Token、密钥、真实节点身份、签名证书、配置备份和未脱敏日志不进入公开仓库或发布包。
8. **验收以原始证据为准。** 明确环境、架构、程序身份和测试范围，保留失败样本；没有真机不能写“已实测支持”。

## 阶段一：macOS 命令行客户端

### 范围与路线

首选新增 `MacOsTunDevice : ITunDevice`，使用 macOS 自带 utun 接口，延续当前命令行产品形态。WireGuard 的 Darwin 实现可作为接口创建、实际名称获取及报文头处理的参考，但参考实现不是本项目已通过兼容性验收的证明。[^R1]

发布延续 Native AOT 方向，当前通过 macOS CI 环境原生构建，不要求拥有本地 Mac；具体 OS/架构与工具链边界按 .NET 官方支持表核对。[^R7]

- 优先适配 `osx-arm64`，并安排 `osx-x64` 的独立原生 CI 构建和自检；不能用单一架构的结果代替另一架构。两者的真机验收均暂缓。
- 初期实现及后续真机验收目标：IPv4、UDP、AES-GCM、MTU 1400、Access Token 接入、稳定虚拟地址、Direct Path、Mesh Route 和 Relay Fallback，以及现有 TCP/UDP Port Tunnel；当前不把真实业务互通计入 CI 已通过范围。
- 保持原配置无参数启动，不要求换用 GUI、重发 Token 或改虚拟 IP。
- 不先引入旧式内核扩展，不要求关闭 SIP；Mac 首版不以系统 VPN 设置中的集成为前提。
- 不将 Linux 的 TUN virtio 元数据、`recvmmsg/sendmmsg` 或 UDP GSO/GRO 常量搬到 Darwin。先实现普通路径与自动化正确性检查，真实性能基线等真机测试恢复后再建立。
- QUIC 不作为首轮数据面验收的必要项。其 macOS 支持、原生依赖与加载限制另行验证；当前微软文档说明仍存在平台限制。[^R3]
- 当前仅记录工具链要求及实际 CI 构建/运行环境。正式最低支持版本仍待真机验证，不能把 CI 镜像或某个系统 API 的最低版本直接当成完整兼容范围。

实现注意事项：

- utun 报文前的地址族头与现有线上帧协议是不同层次，新增后端不能改变其他平台的帧格式。[^R1]
- `Name` 应返回实际接口名；配置中的逻辑节点名称继续用于显示和节点身份。
- 路由创建和撤销必须有归属记录。遇到已有路由、权限拒绝或部分配置失败时，不能删除非本客户端创建的资源。
- 接口读写和路由配置分别可测试；纯逻辑与失败路径使用单元测试覆盖。可用 CI 环境允许时，额外运行 utun 创建/收发/清理冒烟测试；权限或环境不允许时明确跳过，不填入通过数，也不以其替代真机互通。
- 现有 Linux 诊断脚本依赖 `/proc`、`ip`、`tc` 等，需要 Mac 对应实现，不能把缺失指标当成零错误。
- 日志、配置和运行状态不得设计成必须写入未来签名 `.app` 内部；为后续桌面宿主保留独立的可写目录。
- `launchd` 持久运行可在基础互通完成后接入，不改变 CLI 的配置来源，也不默认安装或启用系统服务。

### 暂不阻塞开发的可选方向

系统 VPN 集成作为后续独立决策，不先承担整个 Network Extension 产品化成本。若需要该形态，应使用 `NEPacketTunnelProvider` / Packet Flow 并评估 System Extension、宿主应用、签名与生命周期。[^R2][^R6]

## 阶段二：Avalonia 桌面可视化客户端

启动条件：G1-CI 通过，并记录 Mac 的 CI 验证范围及真机缺口。G1-REAL 暂缓不阻塞本阶段；选择 Avalonia 作为桌面界面框架，不改变已有服务端管理面板的职责。[^R4]

### 架构边界

```text
CLI --------------------------> 共享客户端运行时
                                      |
Avalonia UI -> 受限本地控制通道 -> 网络工作进程
                                      |
                         Core / 平台设备后端
```

当前已有 `Client.Runtime`、`Worker`、`App`、`App.Desktop` 和 `App.Android` 项目；图示表示职责，不表示所有平台已验收：

- CLI 与桌面端共享配置模型、管理 API、端口隧道和 Core 协议。GUI/Android 使用新运行时生命周期；CLI 原有会话宿主仍保留，并未把整个 CLI 生命周期迁入 `ClientSession`。
- 只在实际复用需求出现时抽出最小客户端运行时；不为“未来也许需要”先进行大规模项目拆分。
- UI 以普通用户权限运行；需要特权的设备、路由操作留在受控工作进程或平台服务中。
- 本地 IPC 仅用于有限控制命令与状态，不让每个数据包绕经 GUI 或控制通道。
- IPC 需要调用方身份/访问权限校验，不能退化为任意本地用户都能调用的高权限 HTTP 服务、文件写入或 shell 执行入口。
- 运行时通过有界状态快照、事件和计数暴露信息；不靠解析控制台日志或伪造 UI 计时器推算真实连接状态。

### 首版范围

- 配置：导入已有 `appsettings.json`，编辑服务端、Access Token、节点名称及受支持的连接选项；保存前校验，失败不损坏原文件。
- 连接：实际启动/停止 Virtual Network 与已配置 Port Tunnel，展示连接中、已连接、重连、停止和失败原因。
- 网络状态：真实虚拟地址、加密模式、Peer、当前 Direct Path / Mesh Route / Relay Fallback、上下行速率和累计流量。
- 诊断：筛选/查看日志、脱敏导出诊断信息、显示不支持的协议或平台能力。
- 生命周期：托盘/菜单栏、窗口关闭与断开网络的明确区别、单实例和授权失败处理；自动启动由用户选择。
- 兼容：保持 CLI 可独立工作；允许查看已运行工作进程，而不是再次启动同一 Token 的第二个实例。

首版沿用当前“一个 Virtual Network 配置及多个 Port Tunnel 配置”的能力边界。多个同时活动的 Virtual Network、多份活动配置、完整管理员后台和静默自动更新不顺带加入；如需扩展，单独定义行为、配置迁移和安全验收。

桌面开发目标仍包括 Windows x64、G1-CI 覆盖的 macOS 架构、Linux x64。Windows/Linux 按实际环境验收；macOS 没有真机前只记录构建、自动测试和预览产物，不列为已获真实 UI/数据面验收的平台。Linux ARM64 图形界面作为单独兼容项评估，不因 CLI 已支持 ARM64 就自动承诺图形桌面支持。

UI 采用 MVVM 和清晰的工作视图，围绕反复连接、排障和状态扫描设计，不把客户端做成介绍功能的展示页面。软件渲染、托盘、显示缩放、键盘操作和不同桌面环境的差异按实际支持矩阵验收。[^R4]

优先评估 GUI 的 Native AOT 兼容性，同时把自包含运行和真实交互作为基本要求。CLI 的 AOT 能力不得因引入 UI 丢失；若 GUI 采用不同发布模式，应明确说明，不把托管自包含构建称为 Native AOT。

### G2：桌面验收条件

- [ ] CLI 和 Avalonia 使用同一配置语义、运行时和网络核心，不存在两份会漂移的协议或连接逻辑。
- [ ] 首版范围中的配置、连接、状态、日志和窗口/后台生命周期形成完整可用工作流。
- [ ] UI 不依赖长期 root/管理员身份，IPC、配置写入、凭据展示和诊断导出通过安全检查。
- [ ] 声明已验收的桌面 OS/架构均有真实界面操作、真实数据面、DPI/缩放和恢复证据；当前 Mac 预览范围单独列出，不冒充已验收。
- [ ] Mac 的 CLI/GUI 构建与适用自动测试有可核对证据；真机缺口继续留在 G1-REAL/桌面验收记录中，未被关闭。
- [ ] 关闭窗口、退出应用、停止连接、后台工作进程失败和重启的含义明确且符合实际状态。
- [ ] 与同版本 CLI 对照，没有引入显著的数据面性能回退；测量条件和判定依据有记录。
- [ ] 发布包、依赖、签名、原配置升级与回退通过检查，未运行的平台明确标为未验收。

G2 按明确的已验收平台范围和 Mac 预览范围分别记录。Android 依后续用户要求已启动实现，但这不自动关闭桌面未验收项，也不扩张 Mac 正式支持声明。

## 阶段三：Android 客户端

后续用户已明确选择 Avalonia Android 与 TKCode.Arc.Mobile；工程现已建立。G2 中的其他桌面平台缺口继续记录，不将其伪装成 Android 已通过的依赖。

Android 的重点不是把桌面窗口缩小，而是验证 `VpnService`、系统授权、TUN 文件描述符、传输 Socket 保护和后台生命周期。官方要求保护隧道 Socket 以避免回流，并且同一用户/工作资料中只有一个活动 VPN 服务。[^R5]

### 评估清单

| 编号 | 任务 | 交付物与判定重点 | 当前状态 |
| --- | --- | --- | --- |
| ANDROID-01 | 原生服务与网络接入 | `VpnService.prepare/protect`、TUN 建立与撤销、共享 Core、授权拒绝/撤销、满 MTU、TCP/UDP | x64 模拟器已实测，手机未实测 |
| ANDROID-02 | 后台与恢复 | 前台服务/通知、划掉任务、锁屏 Doze、进程回收、网络切换、耗电与内存 | 改为同进程独立会话服务绑定 VPN 设备；最终 x64 包三轮无 Activity 回收恢复及锁屏/Doze 收发通过；旧失败保留，网络切换及真机耗电待测 |
| ANDROID-03 | 打包与交付 | API 26 起、SDK 36、x64/ARM64 APK、开发签名与正式签名边界 | 双架构 Release 构建入口已建立；不代表 ARM64 手机验收，不发布商店版本 |

评估边界：

- 不假定 Avalonia 的平台支持就能解决 VPN 服务、后台运行和省电限制。[^R4][^R5]
- 优先验证现有 C# 核心在 .NET for Android 中的复用；桌面 RID 和 Native AOT 安装包不能直接当成 Android 应用。
- 传输 Socket 的创建/保护、底层网络绑定和接口生命周期可能需要最小平台钩子，届时以原型证明需求，不在 macOS 阶段预先抽象。
- 配置语义继续复用；实际路径和凭据保护使用 Android 应用私有存储及平台机制，不照搬桌面工作目录。
- 当前功能包括 IPv4、UDP、AES-GCM 的 Virtual Network 和 TCP/UDP Port Tunnel。始终在线、开机启动、全局 DNS、局域网发现及商店发布仍不默认启用或承诺。
- 目标 Android SDK、前台服务声明及应用商店政策在实施时重新核验，不将本文固定为未来合规依据。

G3 按实际构建和实测范围记录。Android 目前定位开发预览；已验证模拟器的恢复不等于任意系统必然保活，真机矩阵、网络切换与正式签名不能被模拟器截图或一次成功构建自动关闭。

## 通用验收与证据

每个里程碑在交付记录中区分：

1. 单元/协议测试与本地构建。
2. 对应 OS/架构的原生构建、加密自检与平台设备测试。
3. 与现有节点的双向真实业务、Direct Path / Mesh Route / Relay Fallback、MTU 和恢复测试。
4. UI 交互与数据面联合验证；截图、Headless 测试和单个平台成功均不能替代其他平台的操作证据。
5. 发布资产、校验值、版本身份、配置兼容、签名状态及旧版恢复。

Mac 真机测试暂缓期间，开发进展按 G1-CI 和实际自动测试报告记录；G1-REAL 不勾选、不删除，也不以“CI 通过”自动关闭。CI 中发生的真实设备冒烟测试仅证明该 runner、权限和用例范围，不等同于最终用户真机环境的完整验收。

性能测量沿用可比较的方法：记录普通网络基线，区分冷启动/稳态、方向和并发；保留完整文件结果、延迟、重传、丢弃、CPU、环境与实际转发路径。平台不存在的 Linux 指标应标为不适用，不能填零。

环境、配置、程序身份和原始证据保留在受控本地目录；公开报告使用匿名化节点与地址，只发布经扫描的源码、说明和干净构建产物。
